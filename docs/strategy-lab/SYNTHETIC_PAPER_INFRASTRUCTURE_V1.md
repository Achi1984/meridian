## 1. Boundary and authority

The permitted harness is isolated, bounded, and test-only:

- All observations, decisions, prices, balances, event identities, and clock
  readings are generated by the test. Use an injected deterministic clock; read
  no machine or provider time.
- Each test gets an ephemeral, isolated account and journal with no shared run,
  account, event, or admission identity. Nothing persists outside the test
  boundary.
- No network, provider, market-data files, real portfolio, production
  persistence, scheduler, daemon, workflow, credentials, spending, or
  provisioning. No public forward/performance export.
- A synthetic event may exercise technical accounting transitions only inside
  this harness. It is never a forward observation, candidate run, strategy
  efficacy result, or performance evidence.
- Synthetic numeric values are fixture parameters, never operating defaults.
  Production `WARMUP_ONLY` classification and its no-forward-decision,
  no-fill, no-account-effect, and no-performance rules remain unchanged.

All real-operation configuration—including strategy/source identity, universe,
product, capital/currency, period, fees/slippage/liquidity, risk/stops/limits,
timing/expiry/marks, freshness/gaps/synchronization, compute bounds, and
reconciliation authority—remains `REQUIRED_UNSET`. Candidate qualification,
source and causal-time evidence, D2 assessment, run admission, and every
operating choice require separate review and authorization.

## 2. Smallest implementation packet

Subject to independent contract/accounting review and an available
implementation lane, the packet may contain only:

1. A pure reducer/accounting function invoked with explicit finite fixture
   bounds; generated input and deterministic clock are passed in, never
   discovered.
2. A fake decision adapter with explicit `NO_ACTION` and action proposals. It
   selects no strategy and supplies no strategy logic.
3. Distinct proposal and commit/ack steps. A proposal alone changes no account
   state. A fake transaction may model all-or-nothing commit, but is not
   persistence evidence.
4. One-effect idempotency: identical identity and digest returns the prior
   modeled result without a second account or cost effect; a changed digest
   under the same identity conflicts and halts.
5. Tests for account/receipt/fence atomicity and compare-and-set behavior,
   including a loser that has no effect and a stale writer that cannot commit.
6. A bounded, read-only result projection distinguishing proposal, committed
   result, rejection, unavailable valuation, and `UNKNOWN`, with no public
   forward/performance export.

For each fixture, declare the exact-decimal or fixed-point representation,
units, scale, and rounding direction/location. Values and rounding choices
belong only to that fixture; they do not choose an operating policy. Require
cash/holding/cost conservation under those explicit fixture rules. Do not use
binary floating-point account arithmetic.

No strategy, new dependency, runtime library, service, workflow, schema, cache,
credential, or production storage is selected or authorized here.

## 3. Persistence and recovery limits

In-memory state and fake-transaction tests can demonstrate model behavior and
atomicity assumptions within the fake. They cannot establish crash durability,
transaction guarantees, or filesystem behavior.

A later, separately reviewed persistence packet may use a bounded local
temporary journal and crash tests only after verifying the existing dependency
and resource are available and suitable. It must not provision resources or
introduce a dependency without a separate contract and security review. Such
tests would evidence only the tested local journal boundary, not production
storage or live operation. Do not reuse
`portfolio-history-store.js` `DOUBLE PRECISION` storage or B1 identity/schema as
an exact-decimal transactional journal.

`UNKNOWN` blocks by default: retain the fence, prohibit dependent effects and
automatic retry, and do not infer success or absence from a lost ACK. The first
technical packet may test that block; it does not implement reconciliation.
The following are proposed semantic acceptance criteria for a future,
separately versioned contract review, **not v1 fields or an adopted schema**:
bind the original operation and immutable evidence to an authorized authority;
distinguish exact original application, authoritative absence, conflict, and
still-unknown; prevent a stale resolver from overwriting current state; make
resolution itself effect-free and duplicate-safe; and never let absence alone
authorize retry. That amendment must define and accept its own receipt,
authority, evidence, and state semantics before reconciliation is implemented
or `UNKNOWN` can resolve.

## 4. Acceptance matrix

“Model” means reducer/fake-transaction behavior only. “Local persistence” is
future evidence from the separately reviewed temporary-journal packet. “Live”
means real provider, production storage, candidate, or Paper operation and is
not tested or claimed by this synthetic packet.

| Case | Required observable outcome | Evidence boundary |
|---|---|---|
| Duplicate event, same identity and digest | Return the prior modeled result; account, state, and fee are unchanged; no second effect. | Model |
| Duplicate event, conflicting digest | Preserve prior committed state; halt with `IDENTITY_CONFLICT`; no second effect. | Model |
| Past/equal event, or no causal ordering proof | No fill or account change; equality is not future; report `LATE_OR_PAST_EVENT` where applicable. | Model |
| Synthetic isolation | Synthetic input is usable only inside its isolated test identity; production treatment remains `WARMUP_ONLY`. No run admission, forward count, account/performance export, or relabeling under the same identity. | Model; live isolation untested |
| Fee once / duplicate fee | One unique fee identity changes cash once; duplicate charge is rejected (`COST_DUPLICATE`); do not subtract a cash-booked fee again from equity. | Model |
| Conservation | Exact fixture arithmetic reconciles cash, holdings, and costs; mismatch rejects the whole proposal with `BALANCE_INVARIANT`, with no partial account update. | Model |
| Stale/missing mark | Valuation is `UNAVAILABLE` with `MARK_UNAVAILABLE`; never substitute zero or carry a stale mark as current. | Model |
| CAS loser | Loser creates no attempt, proposal, receipt, or account effect; winner remains eligible to commit. | Model; local transaction behavior requires later persistence test |
| Stale writer | A writer with an inactive historical fence cannot commit; state and account remain unchanged. | Model; local transaction behavior requires later persistence test |
| Lost ACK after commit | Caller sees `UNKNOWN`; exact read-only lookup may return the original result, with no second balance or cost effect. | Model only in first packet; crash/lost-ACK evidence requires later local persistence test |
| Unknown commit outcome | Keep `UNKNOWN` and active fence; block dependent action and automatic retry; no inference from missing ACK or absence. | Model; crash outcome requires later local persistence test |
| Bound at limit / limit+1 | Exact declared maximum completes if otherwise valid; one over rejects with `BOUND_EXCEEDED`, no truncation or partial mutation. | Model |
| `NO_ACTION` | Record/model an explicit no-action result with no fill or account mutation; it is not strategy-efficacy evidence. | Model |

No row establishes provider availability/authenticity, production persistence,
source causality, strategy efficacy, forward performance, candidate readiness,
or Paper/Live authorization. Those remain explicitly untested or gated.
